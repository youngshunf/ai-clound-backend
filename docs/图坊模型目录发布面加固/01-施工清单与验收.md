## 批次 B1 · 内存与资源边界

### H-01 · OperaLogMiddleware 在路由前全量缓冲请求体

**现状**：`backend/middleware/opera_log_middleware.py:52` 在 `call_next` 之前无条件执行
`args = await self.get_request_args(request)`，其内部 `:194` `body_data = await request.body()`
把整个 multipart 请求体读进内存；`:197-198` 判定非 `application/json` 后
`args['data'] = body_data.decode('utf-8', 'ignore')` 再生成一份等长 str；
`:128` `log.debug(f'请求参数：{request_args}')` 再格式化一份；
`:153` `args=args` 把这个巨串放进 `CreateOperaLogParam` 入队写 `opera_log.args` 列。

发布 817 MB 的 `birefnet-general` 时，service 层 `stage_signed_model_package` 还一行没跑，
`_SIGNED_MODEL_UPLOAD_CHUNK_BYTES` 分块与 `db.rollback()` 提前释放事务全部失去意义；
单次发布进程 RSS 峰值 2 GB 以上，并发两次即 OOM。

> 这是本批最重要的一条：新端点唯一的设计卖点就是「不全量入内存」，
> 而在当前中间件栈下该目标**完全不成立**。

**修法（推荐：中间件级通用闸，而非路径白名单）**

评审给出的方案是把 `/hasn/app-catalogs/` 加进 `OPERA_LOG_REQUEST_DETAILS_PREFIX_EXCLUDE`。
**不采纳为唯一手段**，理由：该前缀会把同一 router 下的 `PUT /{pk}/config` 一并静音，
而那恰恰是 H-04 要求强化审计的写点；且引擎 stage、语音包上传等同类端点仍然裸奔。

改为在 `get_request_args` 里按内容类型与长度短路，覆盖整类问题：

```python
# backend/middleware/opera_log_middleware.py，get_request_args 内、await request.body() 之前
# 大文件上传（模型包/引擎包动辄数百 MB）不得读进操作日志：
# body() 会把整个请求体缓冲进内存，非 JSON 分支还会再 decode 出一份等长字符串，
# 足以让单次发布把 worker 撑爆。这里只记录形状，不记录内容。
content_length = int(request.headers.get('Content-Length') or 0)
if 'multipart/form-data' in content_type or content_length > _OPERA_LOG_MAX_BODY_BYTES:
    args['data'] = f'[BODY OMITTED: {content_type[0] or "unknown"}, {content_length} bytes]'
    return args
```

新增常量（建议 `backend/core/conf.py`，与既有 opera_log 配置放一起）：

```python
# 超过该长度的请求体不读入操作日志，避免大文件上传把 worker 内存打满。
OPERA_LOG_MAX_BODY_BYTES: int = 1 * 1024 * 1024
```

**验收**
- 单测：构造 `multipart/form-data` 且 `Content-Length` 为 100 MB 的请求，断言 `get_request_args`
  返回的 `args['data']` 是占位串、且 `request.body()` 未被调用（用 monkeypatch 计数）。
- 实测：对运行中的 8020 传一个 ≥200 MB 的 zip 到 `/{pk}/model-package-stage`，
  观察进程 RSS 峰值应与包大小无关（`ps -o rss=` 采样），`opera_log.args` 只存占位串。

### H-02 · `catalog.read()` 先全量读入再判 8 MiB

**现状**：`api/v1/admin/hasn_app_catalog.py:279-281`

```python
raw = await catalog.read()                      # 无参数 = 全量读入 RSS
if len(raw) > 8 * 1024 * 1024:
    raise errors.RequestError(msg='图坊模型目录超过 8 MiB 上限')
```

上限形同虚设。`/{pk}/model-catalog` 与 `/{pk}/model-package-stage` 只差一个路径段、
两个端点都收 `UploadFile`，误传几 GB 的模型 zip 会先分配等量内存 → 容器 OOM-Kill →
整台 worker 上所有并发请求一起 502，而不是返回一句「超过 8 MiB 上限」。

**修法**：照抄同文件 `publish_finance_engine_release`（`:172`）的有界读写法。

```python
_MAX_MODEL_CATALOG_BYTES = 8 * 1024 * 1024

raw = await catalog.read(_MAX_MODEL_CATALOG_BYTES + 1)
if len(raw) > _MAX_MODEL_CATALOG_BYTES:
    raise errors.RequestError(msg='图坊模型目录超过 8 MiB 上限')
```

**验收**：传一个 64 MB 文件到 `/{pk}/model-catalog`，断言返回 400 且进程 RSS 无明显抬升。

### H-03 · 4 GiB 上限却走单次预签名 PUT，硬顶 1800 秒

**现状**：`MAX_SIGNED_MODEL_PACKAGE_BYTES` 定为 4 GiB（`service:1069`，注释写明与 daemon
`MAX_PACKAGE_BYTES` 对齐），上传却交给 `StorageService.upload_stream_to_storage` →
`file_ops.write_stream`（`:502-503`）：

```python
upload_timeout = min(1800.0, max(30.0, size / (500 * 1024)))
presign_ttl = int(min(1800.0, max(300.0, upload_timeout)))
```

无论多大都只给 30 分钟、单次 PUT、无分片、无续传。传 2 GiB 的 BiRefNet/SDXL 级包时，
若云端到七牛实际吞吐低于约 1.2 MB/s，第 1800 秒预签名 URL 过期 + httpx 超时 →
`ServerError('上传文件到 S3 失败')` 500，已传的 2 GB 全部作废，只能从零重传。

同仓同量级的语音包路径 `write_immutable_speech_package`（`file_ops.py:529`）恰恰用的是
七牛 `put_stream_v2` + 4 MiB 分片可续传，说明单次 PUT 不是这个体量的可行方案。

**修法**：在 `file_ops.py` 新增 `write_public_package_stream`，复用语音包那套分片上传：

- 走 `put_stream_v2(..., part_size=4 * 1024 * 1024)`，`asyncio.to_thread` 包裹；
- key 已按 `sha256[:16]` 内容寻址，**建议同时带 `insertOnly=1`**：同一包重复 stage 时
  七牛回 `614 file exists`，须显式识别为**幂等成功**而非失败（这正好给 stage 提供了重入语义）；
- 沿用语音包的 `fsizeMin`/`fsizeLimit`/`mimeLimit` 策略与 `returnBody`，
  上传后比对 `result['key']`/`result['size']`——**这一步同时交付 H-15 的回读核对**；
- 非七牛 endpoint 保持现有 `write_stream` 分支，但把 `upload_timeout` 上限从 1800 秒放开
  （改为按 size 线性推算、不设 30 分钟硬顶），并在日志里显式记录推算出的超时值。

**验收**
- 集成：对真实公共桶传一个 ≥1.5 GiB 的 zip，断言成功、`compressed_size` 与桶内一致；
- 重复传同一个包，断言第二次走 `614` 幂等分支并返回相同 `key`/`sha256`；
- 断言非七牛 provider 下仍能上传（可用本地 MinIO/loopback 验证降级分支）。

### H-04 · `PUT /{pk}/config` 整块覆盖可静默抹掉 `signed_catalog`

**现状**：`publish_signed_model_catalog`（`service:1315`）把签名目录写进 `catalog.config_json`；
而同一 router 的 `PUT /{pk}/config` → `hasn_app_catalog_service.update_config`
（`service/hasn_app_catalog_service.py:79`）是**整块覆盖**式写 `config_json`，
两个写点共用同一 `hasn:app:catalog:edit` 权限且互不感知。

运营在 Admin「编辑配置」页改一个模型名后保存，`models.signed_catalog`（以及既有的
`engine` 清单）被静默删除，接口返回 200；`platform_config` revision 变化并推送 invalidate，
全网 daemon 重拉后图坊模型目录消失——已安装模型失效、新节点无法安装，
页面上没有任何报错指向那次保存。恢复必须找回离线签名的原始 catalog 文件重新 POST。

> 这一条同时是 H-08 的前提：它是唯一能把结构非法的 `signed_catalog` 写进库的路径。

**修法（受保护子树，服务端强制）**

在 `update_config` 里把签名子树声明为受保护、不可经通用配置面改写：

```python
# 签名子树由专用发布端点独占写入：通用配置面整块覆盖会静默抹掉全网在用的签名目录，
# 这里强制从入参剥离并回填库中现值，改动只能走 /model-catalog 与 /engine-manifest。
_PROTECTED_CONFIG_SUBTREES = (('models', 'signed_catalog'), ('engine',))
```

- 若入参**试图修改**受保护子树 → 直接 400，文案明确指向对应发布端点；
- 若入参**未包含**受保护子树 → 从库中现值回填，不允许被删除；
- 二者都要，前者防误改、后者防误删。

**验收**
- 单测：库里已有 `models.signed_catalog`，`update_config` 传一个不含该键的 config →
  断言保存后 `signed_catalog` 原样保留；
- 单测：传一个 `signed_catalog` 内容被改过的 config → 断言 400；
- 真实 HTTP：Admin 编辑配置保存一次，断言 `sync_bump` 后 daemon 侧目录仍在。

### H-05 · 重放守卫只认 daemon 两条读路径之一

**现状**：`merge_signed_model_catalog`（`service:1212-1217`）的守卫入口是

```python
current = existing.get('models')
if (
    isinstance(current, dict)
    and isinstance(current.get('signed_catalog'), dict)
    and isinstance(current['signed_catalog'].get('payload'), dict)
):
```

但 daemon 明确同时接受**迁移期直挂形态**——`models` 自身就是签名文档：

```rust
// hasn-node/apps/daemon/src/domains/imagelab/broker.rs:845
let document = models.get("signed_catalog").unwrap_or(models);
```

（`broker.rs:380-393` 的 doc 注释与 `:1282` 的测试都在保这个形态。）

处在迁移形态的 catalog 行，上面那个 `if` 判定为 False，于是整个块——
**低序列拒绝、同序列逐字节幂等、同版本异摘要**——一次都不执行，直接落到 `:1240` 写入。
用一份旧的 `release_sequence` 目录发布会被静默接受；事后 `models` 节点同时存留旧
`payload`/`signature` 与新 `signed_catalog`，daemon 取新的那份，序列回退在两端都无人报错。

引擎孪生 `merge_signed_engine_manifest` 没这个洞，是因为 daemon 读引擎清单只有一条路径；
模型侧移植时读路径由一条变两条，守卫只跟到其中一条。

**修法**：抽一个与 daemon 同语义的读函数，两处都用它取「当前生效文档」。

```python
def _extract_current_signed_model_document(models_node: object) -> dict | None:
    """与 daemon `broker.rs:845` 同语义：优先取 signed_catalog，回落到 models 自身。

    迁移期存在 `models` 直接就是签名文档的形态；守卫必须覆盖两条读路径，
    否则重放/不可变检查会在这些行上整体失效。
    """
    if not isinstance(models_node, dict):
        return None
    candidate = models_node.get('signed_catalog')
    if not isinstance(candidate, dict):
        candidate = models_node
    return candidate if isinstance(candidate.get('payload'), dict) else None
```

写入时仍统一收敛到 `signed_catalog` 键（保持 `:1239` 的既有意图），
**并在检测到迁移形态时把旧的 `payload`/`signature` 顶层键一并清除**，
避免两份文档并存造成后续歧义。

**验收**
- 单测：`config_json = {'models': {'payload': {...seq: 200}, 'signature': '...'}}`，
  用 `seq=100` 的目录发布 → 断言 400「发布序列重放」；
- 单测：同上前置，用 `seq=300` 发布 → 断言成功且 `models` 里不再残留顶层 `payload`/`signature`；
- 单测：同版本异摘要在迁移形态下同样被拒。

### H-06 · 不可变守卫按可变 `dependency_id` 配对

**现状**：`service:1230-1238`

```python
previous_models = previous_payload.get('models') or {}
for dependency_id, incoming_release in incoming_payload['models'].items():
    previous_release = previous_models.get(dependency_id)      # ← 按目录键配对
```

`dependency_id` 只受 `_SIGNED_MODEL_DEPENDENCY_RE = ^model\.[A-Za-z0-9._-]{1,120}$` 约束，
是**发布方自由选取的目录键**；而制品身份实际由 `artifact_id` / `runtime_name` 决定
（`:1120` 强制 `artifact_id = f'app.model.{app_id}.{runtime_name}'`）。

seq=1 发 `models['model.rembg.u2netp']`（runtime_name=u2netp，version=2024.07，sha256=A），
seq=2 发同一模型但键改成 `model.u2netp`（runtime_name、version 不变，sha256=B）：
`previous_models.get('model.u2netp')` 为 None，同版本异摘要检查整段跳过，云端接受。
但 `artifact_id` 仍是 `app.model.imagelab.u2netp`，已装过该 artifact@2024.07（哈希 A）的
daemon 要么判定已安装而不重下（实际跑的是与目录声明不符的旧模型），
要么重下后 sha256 校验失败、抠图在所有终端报安装失败。

代码注释本身写着「避免同一模型在不同发布里指向不同制品目录」，守卫却没按这个身份维度落地。

> **签名工具挡不住这条**：它只验单份文档自洽，跨发布不变量只有云端能守。

**修法**：改按 `artifact_id` 建索引配对（`artifact_id` 在同一份目录内已由 `:1197-1200` 保证唯一）。

```python
# 制品身份（artifact_id）才是跨发布的稳定键；dependency_id 是发布方可自由改写的目录键，
# 按它配对会让同版本异摘要守卫被「换个键重发」直接绕过。
previous_by_artifact = {
    release['artifact_id']: release
    for release in (previous_payload.get('models') or {}).values()
    if isinstance(release, dict) and isinstance(release.get('artifact_id'), str)
}
for dependency_id, incoming_release in incoming_payload['models'].items():
    previous_release = previous_by_artifact.get(incoming_release['artifact_id'])
```

**验收**
- 单测（关键回归）：seq=1 发 `model.rembg.u2netp`/sha256=A，seq=2 发 `model.u2netp`
  （同 runtime_name、同 version、sha256=B）→ 断言 400「同版本异摘要」；
- 单测：换键但同时抬 version → 断言放行（版本变了本就允许换摘要）。

### H-07 · stage/publish 缺 `app_id` 归属校验

**现状**：`stage_signed_model_package`（`service:1269-1272`）与
`publish_signed_model_catalog`（`:1320-1322`）都只判「行存在」，取 `catalog.app_id` 就用；

```python
if catalog.app_id != 'finance':

```

生产上 app-catalog 的 pk 需要现查（施工文档写明「需生产 app_pk」）。把 imagelab 的 pk 记成
film 的 pk 调 stage：只判行存在、取 `app_id='film'`，把 817 MB 包写进

**修法**：两个入口都在取 `app_id` 之后立即加归属闸，文案直指选错应用。

if catalog.app_id != _SIGNED_MODEL_APP_ID:

**验收**
- 单测：用 `app_id='film'` 的 catalog 行调 stage → 断言 400 且**未发生任何上传**
  （mock `upload_stream_to_storage` 断言零调用）；
- 单测：同上调 publish → 断言 400 且 `config_json` 未变更。

### H-08 · `package` 为 null 时守卫抛 AttributeError → 500

**现状**：`service:1236`

```python
and previous_release.get('package', {}).get('sha256') != incoming_release['package']['sha256']
```

`dict.get(key, default)` 的 default **只在键不存在时生效**；`package` 键存在但值为 `null`
时返回 `None`，`None.get('sha256')` 抛 `AttributeError` → 未捕获 → 500。

触发前提是库里已有一份 `package` 为 null 的历史目录，而这正是 H-04 那条绕开校验的
`PUT /{pk}/config` 能造出来的。管理端只看到「服务器内部错误」，
本该是一条可读的 400；同时这条不可变守卫在该分支上等于失效。

**修法**：

```python
previous_package = previous_release.get('package')
previous_digest = previous_package.get('sha256') if isinstance(previous_package, dict) else None
if (
    isinstance(previous_release, dict)
    and previous_release.get('version') == incoming_release['version']
    and previous_digest != incoming_release['package']['sha256']
):
```

注意：`previous_digest` 为 `None` 时应**继续判为不一致并拒绝**（现有语义即如此），
而不是跳过——历史数据残缺时保守拒绝，让运维显式修复。

**验收**：单测构造 `previous.package = None` 与 `previous.package = 'x'` 两种脏数据，
断言均返回 400 而非 500。

## 批次 B3 · 校验对齐（纵深补齐）

> 本批 5 条都是 **B 类**：签名工具的 `sign-models` 自检已用 daemon 同款验证器挡过一道，
> 正规工具链产出的目录不会带着这些非法值到云端。补齐的价值是
> ①云端是全网分发前最后一跳、②模块注释自称「挡住明显残缺的发布」、
> ③引擎孪生实现都有、模型侧移植时丢了，不对称本身就是后续误改的温床。
> **因此本批统一按「一次提交、逐项对齐」处理，不单独排期。**

### H-09 · 包 key 缺 `..` 与空白字符拦截

`service:1093` 只做前缀判断；引擎孪生 `:561-566` 还有 `'..' in object_key` 与
`any(character.isspace() ...)`。daemon `validate_package`（`model_artifact.rs:259-262`）
拒绝 `key.contains("..")` 与控制字符。

```python
if (
    not isinstance(object_key, str)
    or not object_key.startswith(expected_prefix)
    or '..' in object_key
    or any(character.isspace() for character in object_key)
):
```

### H-10 · size 系列无 4 GiB 上界

`service:1101-1104`（package 的 `compressed_size`/`installed_size`）与 `:1146-1148`
（release 的 `size`）都只判正整数。daemon `validate_model`/`validate_package`
判 `> MAX_MODEL_BYTES` / `> MAX_PACKAGE_BYTES`（均为 4 GiB，`model_artifact.rs:30-31`）。
同一提交在 stage 路径（`:1069`）专门对齐了这个上界，发布路径却没重建。

三处统一加 `or size > MAX_SIGNED_MODEL_PACKAGE_BYTES`，错误文案带上上限值。

### H-11 · 包 url 放行明文 http

`service:1096` 是 `urlparse(url).scheme not in {'http', 'https'}`；
引擎孪生 `:568-574` 与 daemon `PackageSourceRef::parse`
（`crates/hasn-local-runtime-artifact/src/contract.rs:44-75`，注释写明「只接受 https，
或 loopback 上的 http」）都严格得多。macOS 桌面端 ATS 默认拒绝明文 HTTP，
一旦放行会造成「Linux/Windows 装得上、macOS 装不上」的平台分叉故障。

直接复用引擎侧写法：

```python
parsed_url = urlparse(url)
loopback = parsed_url.scheme == 'http' and parsed_url.hostname in {'localhost', '127.0.0.1', '::1'}
if parsed_url.scheme != 'https' and not loopback:
    raise errors.RequestError(msg=f'图坊模型目录 {runtime_name} 的包 url 必须是 HTTPS 或 loopback HTTP')
```

### H-12 · `schema_version` 裸相等放行 `true` / `1.0`

`service:1171` 是 `if payload['schema_version'] != 1`。Python 里 `True == 1` 且 `1.0 == 1`，
所以 JSON 的 `true` 与 `1.0` 都能冒充 schema v1。同一函数对 `release_sequence`、`size`
都显式加了 `isinstance(x, bool)` 排除，这里漏了。

```python
schema_version = payload['schema_version']
if not isinstance(schema_version, int) or isinstance(schema_version, bool) or schema_version != 1:
    raise errors.RequestError(msg='图坊模型目录 schema_version 必须为 1')
```

### H-13 · token / display_name / filename / license 四处漂移

| 位置 | 现状 | daemon 要求 | 修法 |
|---|---|---|---|
| `:1117` `runtime_name`<br>`:1265` stage 同名字段 | `_SIGNED_ENGINE_TOKEN_RE` 能匹配 `.` 和 `..` | `is_safe_token` 显式 `value != "."` / `!= ".."`（`model_artifact.rs:278-279`） | 比照紧邻的 `version`（`:1141`）加 `in {'.', '..'}` 排除 |
| `:1126` `display_name` | `len(display_name) > 128` 按**字符**计 | `model.display_name.len() > 128` 是 Rust 的**字节**长度 | 改 `len(display_name.encode('utf-8')) > 128`；50 个汉字 = 150 字节，现状会放行、daemon 会拒 |
| `_SIGNED_MODEL_FILENAME_RE` | `^[A-Za-z0-9._-]{1,128}\.onnx$` 总长可达 **133** | `value.len() <= 128`（含 `.onnx`） | 收紧为 `{1,123}`，或加显式总长断言 |
| `:1138` `license` | 仅判非空字符串 | `spdx::Expression::parse(&model.license).is_err()` 即拒（`model_artifact.rs:245`） | 用 `license-expression` 库解析；若不愿引依赖，至少加白名单校验（现役取值为 `Apache-2.0`/`MIT`） |

> `runtime_name` 的 **stage 半边（`:1265`）是 A 类**：stage 在签名之前，
> 填 `..` 会让 object_key 变成 `runtime-model/imagelab/../<version>/...`，
> 服务端把整个 1 GB zip 读完、算完 sha256、`rollback` 之后，
> 才在 `write_stream` → `_clean_object_path` 抛出一个与 `runtime_name` 无关的模糊 400，
> 带宽和临时磁盘已全部消耗。**必须在 `:1265` 前置拦截。**

**本批验收**：为每条漂移补一个 `test_validation_rejects_*` 参数化用例
（现有文件已有 `test_validation_rejects_malformed_catalog` 的 `mutate` 参数化骨架，直接扩展）。

## 批次 B4 · 健壮性与收尾

### H-14 · `is_zipfile` 仅探测尾部 EOCD

`service:1285` `zipfile.is_zipfile(upload.file)` 只在文件尾部 64 KiB 内找 EOCD 魔数
（CPython `_check_zipfile` 仅调 `_EndRecData`），且吞掉 `OSError` 返回 False，
断不了 docstring 承诺的「可读取的 ZIP 文件」。前半段被截断/损坏但尾部中央目录完整的 zip
照样通过 staging，被签进目录发布上线。

daemon 安装时会逐文件比对摘要（`driver.rs:520` `verify_expanded` →
`archive.rs:291` `FileDigestMismatch`），**不会装错模型**，
但代价是一个 release_sequence 已被消耗，只能走「重传 + 重签 + 抬序列」。

**修法**：改为真正读一遍中央目录并做结构断言。

```python
with zipfile.ZipFile(upload.file) as archive:
    if archive.testzip() is not None:
        raise errors.RequestError(msg='图坊模型包存在损坏条目')
    entries = [item for item in archive.infolist() if not item.is_dir()]
    if len(entries) != 1 or not entries[0].filename.endswith('.onnx'):
        raise errors.RequestError(msg='图坊模型包必须恰好包含一个 .onnx 文件')
```

顺带把 `filename`/`installed_size` 与包内实际条目对上，让 stage 返回值更可信。
注意 `testzip()` 会完整解压校验 CRC，对 GB 级包有耗时成本——
若实测不可接受，退化为「只读中央目录 + 条目数/扩展名/解压后大小断言」，不做 CRC 全量校验。

### H-15 · 回读核对 + 真实 HTTP 冒烟 + ruff 收尾

**(a) 上传后回读核对**（若 H-03 采用七牛 `put_stream_v2` 方案，此项由 `returnBody`
比对天然交付，只需补非七牛分支）：

stat = await StorageService.stat_on_storage(storage, object_key=object_key)

### 2. H-13 的 license 走「不引依赖」分支

环境内没有 `license-expression` / `spdx-tools`，为一条 B 类纵深校验引入新运行时依赖
不成比例。改为 `_SPDX_EXPRESSION_RE` 做 **SPDX 表达式语法**校验（许可证 id 字符集 +
`AND`/`OR`/`WITH` + 括号）：挡得住现实中真会发生的 `Apache 2.0`（带空格）、`商用授权`
（中文），但不校验 id 是否在 SPDX 官方清单内——后者由 `sign-models` 自检兜底。
边界已写进函数 docstring。

### 3. H-03 最终**不加** `insertOnly`（与并发提交的语义冲突）

本文原方案建议七牛分支带 `insertOnly=1`，把重复 stage 的 `614 file exists` 判为幂等成功。
施工期间另一会话在同一函数落了 `7cf7d513`「按内容寻址幂等复用已上传对象」——上传前用
**服务端复算摘要**判断是否可跳过，摘要不符时的语义是**覆盖重传**（其提交信息记录了
817 MB 包超过 nginx `proxy_read_timeout` 触发 504 的真实事故）。

两者叠加会产生一个单独看各自都正确的缺陷：

- 桶内残留一个上一次中断留下的**同 key 异内容**残包；
- 复用检查发现摘要不符 → 返回 `None`，意图覆盖重传；
- 但 `insertOnly` 让覆盖变成 `614` → 被判为「幂等成功」直接返回；
- 于是每次重试都"成功"，URL 却始终指向那份坏字节，**残包永远修不好**。

解决：`write_public_package_stream` 去掉 `insertOnly` 与 614 分支，只保留
`fsizeMin`/`fsizeLimit`/`mimeLimit` 锁死大小与 MIME。「跳过重复上传」完全交给上传前的
摘要复用检查，覆盖能力保留给残包修复。回归测试
`test_upload_token_is_not_insert_only` 断言上传凭证里不得出现 `insertOnly`。
